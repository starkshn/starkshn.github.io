Resources & Object

Addressable

❓구현이유

고전적인 방식인 Resource.Load 방식을 사용하게 되면 빌드시 Resource폴더에 존재하는 모든 에셋들을 로드하게 되는 문제점과 경로가 변경되면 코드에 문제가 될 수 있는 부분들이 있어서 경로를 자동으로 추적해주고 리소스 관리를 보다 편리하게 해줄 수 있는 Addressable 기능을 통해 리소스를 관리하게 되었습니다.

>

기존 Resource폴더에서 리소스를 관리할 때와 Addressable을 사용할 때의 리소스 양의 차이점을 표현해 보았습니다.

기존 방식은 어떠한 이유로 사용하지 않는 리소스도 포함하는 반면 Addresaable은 그렇지 않은것을 보여주고 있습니다.

>

Addressable로 리소스들을 관리 및 라벨 설정

💻 코드

매개 변수에 라벨이름, 현재 로드 개수, 전체 로드 개수를 넣으면 비동기로 처리됨에 따라 callback함수를 호출 받아 현재 몇개의 리소스가 로드가 될 수 있는지 확인할 수 있는 코드입니다.

>

실사용 코드입니다. callback함수를 람다로 작성하여 로그를 통해 정상적으로 로드가 되었는지 확인할 수 있습니다.

>

Addressable 서버 Remote 빌드 및 리소스 관리(Render서버)

❓구현이유

기존에 어드레서블의 장점을 이용하여 리소스를 로드할 수 있는 부분이 있지만 간단한 데이터 수정이 발생하거나 리소스의 일부분이 수정된 경우 다시 재빌드를 하여 배포를 해야하는 문제가 있습니다. 간단하게 리소스만 변경하는 경우 Remote로 서버에서 리소스를 다운 받아 사요하면 클라의 리소스 용량 감소 + 빌드 없이 패치할 수 있다는 장점이 생기게 됩니다.

>

📕 도식화

위 순서대로 나온 결과물을 Render서버에 올려두고 유니티에서는 해당 bundle파일을 비동기 로드하여 리소스를 로드할 수 있습니다.

>

🛠️ 개발 순서

  1. Git Repo 생성
  2. Render → Static Site 생성
  3. Git Repo에 XML파일 업로드
  4. 유니티 연동
Render를 통해 XML를 배포할 사이트 생성 및 빌드와 빌드 성공적 확인 완료

>

올라간 데이터 배포를 확인

>

유니티 어드레서블 Remote.LocalPath 설정

>

유니티에서 어드레서블 빌드 확인

>

빌드 결과물 Render 레포지토리에 업로드

>

XML데이터 Data라벨로 변경

>

어드레서블 Data 설정파일 Remote로 변경

>

Addressables.LoadResourceLocationsAsync 함수로 로드 정상 확인 완료하였습니다.

이제 데이터 변경이나 리소스 변경이 있다면 로컬에서 작업 후 깃에 커밋하여 유니티에서 빌드만 해주면 배포가 완료됩니다.

ResourceManager

❓구현이유

Addressable로 로드한 데이터들을 Manager라는 중간 단위 매개체를 통해 관리하기 위한 목적으로 구현하였습니다. 또한 풀링을 사용하는 데이터인 경우에 대한 처리를 위해서 필요하다 판단이 되어 구현하게 되었습니다.

>

📕 도식화

ResouceManager의 중간 역할

>

실제로 어떤 객체가 요청할때 동작 방식

>

💻 코드

비동기로 로드한 객체를 _resources라는 자료구조에 원본을 저장하고 있는 코드입니다.

>

어떤 객체가 리소르를 필요로 할 때 위 함수를 요청하게 될 때 동작방식의 코드입니다.

해당 리소스가 풀링이라면 PoolManager로부터 Pop하여 반환하고 그렇지 않다면 prefab을 기반으로 해당 객체를 생성하여 반환합니다.

>

PoolManager

❓구현이유

게임 특성상 수많은 오브젝트를 생성하고 삭제하는 컨텐츠가 들어가게 됩니다. 이때 매번 새로운 객체를 생성하고 삭제하게 되면 메모리 단편화로 인한 성능저하가 확실하기 때문에 오브젝트 풀링을 통해 이를 방지하고자 구현을 하게 되었습니다.

>

📕 도식화

💻 코드

유니티 2021부터 공식 지원하는 IObjectPool을 통해 구현한 Pool 클래스입니다.

객체가 생성될 때 수행할 콜백함수를 4개를 정의하여 동작을 수행할 수 있도록 유도하였습니다.(SetActive)

>

여러 Pool을 가지고 있는 PoolManager의 클래스 코드입니다.

>

ObjectManager

❓구현이유

PoolManager & ResourceManager와 컨텐츠 코드(SpawingPool 등)와의 중간 매개체 역할을 하고 오브젝트를 관리하는 객체가 필요하다 판단이 되어 구현하게 되었습니다.

>

📕 도식화

연두색으로 칠해진 ObjectManager가 중간 매개체 역할을 하면서 Spawn을 요청하면 PoolManager에게 풀링한 오브젝트를 반환 받을 수 있도록 합니다.

>

💻 코드

Spawn와 Depsawn에 관련된 코드입니다. Instantiate코드는 내부적으로 PoolManager에게 Pop또는 Push를 요청하도록 구현되어 풀링을 사용하도록 구현되어 있습니다.

>

SpawningPool

❓구현이유

PoolManager로 부터 필요한 리소스를 요청하는 “컨텐츠 객체”역할을 수행하는 객체입니다.

실제 컨텐츠에 필수적인 요소로 오브젝트 생성을 빠르고 간편하게 요청 및 생성하기 위해서 만든 객체입니다.

>

📕 도식화

💻 코드

_maxSpawnCount와 코루틴을 통해 PoolManager로부터 오브젝트를 Spawn할 수 있도록 기능을 수행하는 코드입니다.

레벨에 배치된 오브젝트 수가 _maxSpawnCount보다 작다면 _spawnInterval을 두어 코루틴 함수를 통해 오브젝트를 Spawn합니다.

>

Gird

❓구현이유

충돌 및 몬스터가 죽고 나서 아이템을 떨구었을 때 플레이어가 해당 아이템을 줍기위한 조건 등 다수의 오브젝트가 씬에 있는 경우 이들을 효율적으로 관리하고 사용하기 위해 Grid와 더불어 Grid를 Cell이라는 단위로 나누어서 관리하고자 구현을 하였습니다.

📕 도식화

각 Cell별로 오브젝트를 관리하는 모습을 표현하고 플레이어가 Cell별로 특정 오브젝트를 찾는 과정을 표현

플레이어의 min/max 탐색 범위를 두어 해당 범위에 걸치는 모든 Cell을 가져오고 각 Cell이 포함하고 있는 오브젝트들을 가져오는 아이디어입니다.

>

🛠️ 개발 순서

Gird Component로 맵을 잘 게 쪼개기

>

각 칸에 Cell이라는 단위 부여

>

💻 코드

GirdController의 Cell에 오브젝트를 추가(Add)하는 함수, Cell로 부터 오브젝트를 삭제시키는 함수(Remove), 월드 좌표로 부터 해당하는 Cell을 찾는 함수(GetCell)

range에 걸치는 모든 Cell로부터 각 Cell이 가지고 있는 오브젝트를 List로 반환하는 함수

Skill

Skill 구조

❓구현이유

여러 스킬을 효율적으로 관리하기 위한 일종의 작은 매니져 클래스를 구현하였습니다.

게임 특성상 스킬이 많은 게임이기 때문에 SkillBook이라는 컴포넌트를 만들어 스킬들을 관리하려 구현하였습니다.

>

📕 도식화

오브젝트는 Controller(컨트롤 담당) SkillBook(스킬 담당)컴포넌트를 가지고 있는 형태입니다.

스킬은 ‘반복스킬’, ‘단발스킬’로 나뉘는 구조이며 SkillBook은 Manager처럼 Skill들을 List로 관리하는구조입니다.

>

🛠️ 개발 순서

  1. Boss 몬스터 기준 스킬을 생성
  2. SkillBook에 생성한 스킬을 등록
  3. SkillBook에서 원하는 로직대로 Skill을 수행 및 제어

💻 코드

보스 몬스터의 초기화 부분에서 스킬을 Skills에 등록하고 사용할 준비를 하는 코드입니다.

>

실제로 스킬이 끝날 때 마다 다음 스킬 사용준비를 하는 코드입니다.

>

실제 스킬을 사용하는 코드입니다. 원하는 로직을 코루틴 함수에서 실행하고 끝났다면 callback함수를 호출하여 종료합니다.

>
